# Cloudflare Tunnel runtime

The Node primary process manages one `cloudflared` child after an HTTP worker is ready. `isCloudflareTunnelEnabled` defaults to true; with CDN off, first startup creates a quick tunnel without requiring a preexisting name. Cloudflare's generated hostname label is saved as `cloudflareTunnelName` on every successful quick creation. It is not displayed in the Client UI.

With CDN on, the manager requires a saved nonempty name and the saved Cloudflare email, zone ID, and global API key. The Client CDN enabling modal collects those credentials plus a required fourth **Cloudflare Tunnel Name** input. It never prefills a generated quick name. Missing/invalid configuration reports an error without stopping local Node access or falling back to a quick tunnel.

Successful CDN enablement atomically saves the supplied name/credentials, then reconciles as named when tunnels are enabled. With tunnels off, configuration is saved and the connector remains stopped. Disabling CDN restores owned DNS using the old credentials before clearing them, then reconciles as quick only when tunnels are enabled; every successful quick creation saves the new generated name. These lifecycle effects run on Node even without an open Client page.

## Installation

- npm distribution: postinstall downloads only the current host's cloudflared 2026.10.7 executable into `resources/cloudflared/<platform>-<architecture>/`, verifies the pinned SHA-256 checksum, and sets executable permissions. Windows x64, Linux x64/arm64, and macOS x64/arm64 are supported. Node selects its package-relative executable independently of the working directory. macOS archives and extracted executables are both verified. A valid existing binary is reused, and installation stages a replacement before an atomic rename. Failed downloads retain any previous executable. The upstream license and release attribution ship with the installer.
- Source checkouts/manual retry: run `npm run install:cloudflared` in the Node package directory, or `npm run install:cloudflared --prefix <installed-package-directory>` from elsewhere. Alternatively install an architecture-appropriate [official cloudflared binary](https://developers.cloudflare.com/tunnel/downloads/) on PATH, or set `MOARTUBE_CLOUDFLARED_PATH` to its executable path. The override takes precedence; PATH is the fallback when no package-local executable exists. Native Windows arm64 and other unsupported targets require a compatible separately installed binary. The Node validates `cloudflared --version`; Windows child windows are hidden.
- Docker: the production image includes cloudflared 2026.10.7 for amd64/arm64, pinned using the official SHA-256 asset digests in `scripts/install-cloudflared.mjs`. The installer verifies the digest before writing the executable. The image includes the CA certificates needed for the connector's HTTPS requests.
- Permit the connector's required outbound network access. The origin is local HTTP at `127.0.0.1:<nodeListeningPort>`; no inbound router port is required for tunnel traffic.

The Node starts a public quick tunnel by default when this feature is enabled. Use **Cloudflare Tunnels**, to the right of **Cloudflare Turnstile** in Client settings, to stop/start either mode. Off retains the name/CDN configuration and remains effective across starts; on uses the current CDN mode. For initial unattended configuration, set `isCloudflareTunnelEnabled` to `false` in Node settings before startup. Do not use an empty name as an off switch.

For npm releases, `npm pack`/`npm publish` runs `prepack` to build Node. The package allowlist includes the built runtime, launchers, installer scripts, upstream license/attribution, and runtime documentation; generated binaries are excluded even when present locally. `scripts/cloudflared-release.mjs` pins release asset names/digests shared with Docker. Publishing does not download executables. No executable is downloaded at Node startup.

Installation needs outbound GitHub access. Automatic postinstall warns without failing Node installation if the download is unavailable, fails verification, or the platform is unsupported; local HTTP remains usable and the tunnel manager reports an executable error if none is available. The manual installer exits unsuccessfully on failure, allowing deployment scripts to require a successful install. npm installations with lifecycle scripts disabled must run the manual command or supply an executable. Set `MOARTUBE_SKIP_CLOUDFLARED_INSTALL=1` or `MOARTUBE_CLOUDFLARED_PATH` before installation to skip the automatic download. Docker uses the skip flag during dependency installation, then performs its own architecture-specific build download. Existing permission repair/private temporary-copy handling remains available for manually copied or read-only installations.

Authenticated `POST /settings/cloudflare/tunnel/toggle` accepts `{ "isEnabled": boolean }`; the Client proxies it at `/settings/node/cloudflare/tunnel/toggle`. The response reports `settingsSaved`, actual saved flags/name, and runtime state. HTTP 502 with `settingsSaved: true` means the preference was saved but lifecycle reconciliation failed; it is not a settings rollback. The Client keeps partial-save fields, refreshes settings/runtime, and makes the toggle available again after the request. A lock conflict returns 409 without changing the preference.

## State and ownership

Node/watch/embed pages use relative Node assets and filesystem media sources, allowing direct access and tunnel access without rewriting `publicNodeProtocol`, `publicNodeAddress`, or `publicNodePort`. Those fields still select configured public links and participate in CDN/named-host configuration. S3 media follows its configured S3/CDN base independently of the tunnel. The filesystem `/external/videos/baseUrl` API now returns an empty base and filesystem source APIs return Node-relative paths; consumers must resolve them against the responding Node origin. MoarTube Client does this using its actual connection address, including IPv6 and mapped ports.

Managed HLS references are document-relative at creation/upload/migration. Existing filesystem playlists are normalized during GET without rewriting stored files. Settings-driven migrations normalize filesystem/S3 manifests and preserve rendition-before-master ordering, retry/rollback, and cache invalidation. `_media_url_origins.json` records non-secret prior media bases atomically before settings changes, enabling recovery after a partial migration/restart. Retain it with Node data. Intentionally external or signed/query-bearing references are preserved. A legacy managed URL from an unknown former origin reports incomplete migration rather than being rewritten blindly; restore its trusted former base in the origin-history array under maintenance and retry the distribution operation. No credentials or URL query signatures belong in that file.

Canonical public links prefer a valid configured public origin, then an actually ready quick-tunnel URL when applicable; local-only share links are identified as such. Stopped/failed tunnels are not advertised as ready, and background callers cannot invent a public localhost fallback. Node trusts loopback proxies rather than all peers; arbitrary forwarded headers do not become canonical links. Quick-origin snapshot reads time out after two seconds without spawning a connector. Root-mounted deployments are supported; arbitrary reverse-proxy path prefixes and new private-HLS authentication schemes are outside this change. See the [URL policy](../../MoarTube-Client/docs/cloudflare-tunnel-url-policy.md).

Public/direct browser watch and embed playback, seeking, asset loading, share links, and WebSocket connections passed with isolated synthetic media. Direct playback and local sharing survived tunnel disable, off persisted across restart, and a fresh quick hostname worked without rewriting stored playlists/public settings. Test containers/anonymous data volumes were removed after clean shutdown. Live named-account/CDN/storage-provider transitions and remaining platforms are still milestone 6 work. Restart an existing Node process to load the updated build.

Authenticated `GET /settings/cloudflare/tunnel` returns `{ isError: false, tunnel: { mode, status, name, publicUrl?, message? } }`. It is a snapshot and never initiates provisioning. Desired enablement/CDN flags remain in the existing settings response; runtime errors do not silently rewrite preferences.

Workers use correlated primary-process IPC requests through `requestTunnelOperation` for status/reconcile/restart. They never spawn connectors. Shutdown cancels pending startup/retries, waits for connector termination, and suppresses worker respawn.

Named provisioning resolves the account through the saved zone, creates or reuses the privately recorded tunnel UUID, configures ingress for the Node hostname (and filesystem media hostname), reconciles that hostname's DNS, and fetches a connector token. S3 media DNS remains independent. Provider permissions must permit zone lookup, tunnel operations, and DNS changes; CDN credential validation alone does not prove these permissions.

`_cloudflare_tunnel_private.json` in the Node data directory records owned UUIDs and original DNS record snapshots. It is written atomically with restrictive permissions and contains no connector token or API key. Tokens are held in memory and passed through `TUNNEL_TOKEN`, never command-line arguments. Each child uses an isolated empty configuration, and inherited tunnel-specific environment options are removed. Raw connector/provider output is not written to Node logs or returned to clients.

Only the Node's recorded UUID is reused; resources are never adopted or deleted by matching a display name. A definite missing/deleted recorded UUID permits recreation; an authorization/network failure does not. Replacement intent records both old and pending owned UUID targets before DNS changes. Multiple conflicting records or externally edited active managed records produce an error rather than destructive reconciliation. Remote tunnel ownership survives connector stop for reuse. CDN disable restores original owned DNS records (or deletes an owned alias with no predecessor), retaining snapshots and marking routes released so failed provider changes can roll back. Released records subsequently edited externally are left alone. Obsolete owned hostnames are restored after new routes are configured; S3 media handoff preserves its explicitly configured target.

Restoration does not stop an active connector; the connector changes mode only after settings commit. Cross-zone cleanup runs inside provider rollback boundaries before committing new credentials. Keep the journal with Node data when moving installations. An unjournaled just-created resource is deleted if its initial journal write fails. If that compensating deletion also fails, automatic provisioning stops: repair storage and inspect the Cloudflare account before explicitly retrying to avoid creating repeated untracked resources.

Provider/distribution work uses a shared cross-process tunnel admission lock before the settings writer lock. Concurrent conflicts return 409 without saving. Disabling bypasses provider admission so connector cleanup can proceed promptly. Before spawning, the primary strictly reloads settings and compares the desired configuration while holding the writer lock; a newer disable or configuration change rejects stale startup. Unreadable settings suspend startup instead of using cached enablement. Matching pending requests are coalesced, superseded queued operations are discarded, and unchanged healthy settings keep the existing connector. Changed named credentials/name/routes/origin trigger reconciliation.

## Failure handling and verification

Readiness requires a registered connection and, for quick mode, a valid generated URL. A generated-name persistence failure stops/reconciles the new child. A connector that cannot be stopped retains its handle, preventing another launch. Graceful termination escalates to forced termination after five seconds and reports failure if it still cannot stop.

Unexpected exit/startup errors have five bounded retries (1s, 5s, 15s, 30s, 60s). Each retry rereads committed settings; a disabled preference cancels creation. Explicit reconcile/restart starts a fresh retry budget after exhaustion. Failed stops retain the handle and retry cleanup; stop-only retries never create a replacement. Requested-stop exit callbacks do not schedule a restart. Local HTTP access remains available during connector errors.

Tests use controlled child processes and mocked Cloudflare responses for lifecycle, cancellation, persistence failures, ownership/DNS, and cluster readiness/shutdown. Live named-tunnel checks require a configured test Cloudflare account; no account credentials are needed for quick-mode checks. Cross-platform and full UI transitions remain in milestone 6.
